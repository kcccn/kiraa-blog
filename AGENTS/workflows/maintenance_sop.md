# 标准化作业流程（SOP）

> 本流程为 Theme Expert 角色的强制执行框架。每个步骤的输入、输出和判断标准均为硬性要求，不得跳过或简化。

---

## Step 0（强制）：查阅记忆

**触发时机**：收到任何用户需求后，执行 Step 1 之前

**操作**：

1. 读取 `AGENTS/knowledge/dev_log.md`
2. 检查"第一部分：核心架构决策（ADR）"中的所有条目，确认即将执行的方案不违反任何 ADR
3. 检查"第二部分：踩坑与日常维护记录"中是否存在与当前需求相关的历史记录，避免重复踩坑

**输出**：记忆检查结果

| 检查项 | 结果 |
|--------|------|
| 是否违反 ADR-001（禁止修改 themes/） | 是 / 否 |
| 是否违反 ADR-002（强制 KaTeX） | 是 / 否 |
| 是否违反 ADR-003（Vue 配色体系） | 是 / 否 |
| 是否违反 ADR-004（覆盖优先级链） | 是 / 否 |
| 是否违反 ADR-005（暗色模式验证） | 是 / 否 |
| 是否存在相关踩坑记录 | 是 / 否（附记录摘要） |

**判断标准**：任何检查项为"是（违反）"时，立即终止流程，向用户报告冲突并要求确认。不得在违反 ADR 的情况下继续执行。

**异常处理**：

| 异常 | 处理方式 |
|------|----------|
| 用户需求明确要求违反 ADR | 终止流程，输出冲突报告，要求用户修改需求或更新 ADR |
| 踩坑记录中存在相关约束 | 将约束纳入方案设计，在输出中标注引用来源 |

---

## Step 1：需求分析

**输入**：用户描述的需求或问题

**操作**：

1. 确认需求类型：
   - 样式修改 → 进入样式修改子流程
   - 功能添加 → 进入功能添加子流程
   - Bug 排查 → 进入诊断子流程
2. 确认影响范围：
   - 页面类型：首页 / 文章页 / 归档页 / 全局
   - 渲染模式：亮色 / 暗色 / 双端
3. 将需求转化为可量化的规格（颜色值、尺寸、配置项名称等）

**输出**：需求规格文档，包含类型、范围、量化指标

**判断标准**：规格文档必须包含具体的属性值，不接受模糊描述

**异常处理**：

| 异常 | 处理方式 |
|------|----------|
| 需求涉及 `themes/FixIt/` 内文件 | 拒绝执行，说明必须通过覆盖方式实现（ADR-001） |
| 需求无法量化 | 要求用户补充具体指标 |

---

## Step 2：方案设计

**输入**：Step 1 输出的需求规格文档

**操作**：

1. **样式修改**：定位目标 CSS 变量或 SCSS 选择器
   - 优先在 `assets/css/_custom.scss` 中搜索已有覆盖规则
   - 其次在 `themes/FixIt/assets/css/_variables.scss` 中查找 SCSS 变量默认值
   - 最后在 `themes/FixIt/assets/css/_core/_root.scss` 中查找 CSS 变量输出（`--fi-*`）
2. **功能添加**：定位目标配置项或模板
   - 优先查阅 `hugo.toml` 中是否已有相关配置
   - 其次查阅 `themes/FixIt/layouts/` 中相关模板
   - 确认 FixIt 主题是否已内置支持
3. 确定实现路径（按 ADR-004 优先级链选择）：
   - 路径 A：CSS 变量覆盖（`:root` 块）
   - 路径 B：SCSS 选择器覆盖（`.single .content` 内）
   - 路径 C：hugo.toml 配置调整（含 `customPartials` 扩展；若组件需要自定义 JS 生命周期，优先配合 `assets/js/custom.js` 实现）
   - 路径 D：项目 `layouts/` 模板覆盖（全文件替代，最后手段）

**输出**：方案文档，包含目标变量/配置项、当前值、目标值、实现路径

**判断标准**：

- 实现路径必须符合 ADR-004 优先级链
- 方案不得涉及 `themes/FixIt/` 目录下的文件修改
- 暗色模式适配方案必须明确（ADR-005）

**异常处理**：

| 异常 | 处理方式 |
|------|----------|
| 目标属性无对应 CSS 变量 | 降级为路径 B（选择器覆盖），记录降级原因 |
| 目标属性被 `!important` 覆盖 | 新规则同样使用 `!important` |
| 功能需要修改主题源码 | 拒绝执行，说明需等待主题更新（ADR-001） |

---

## Step 3：编写覆盖代码

**输入**：Step 2 输出的方案文档

**操作**：

1. 按方案文档中确定的路径编写代码
2. 遵循项目现有格式：
   - SCSS 使用 4 空格缩进，注释使用 `/* */` 格式
   - CSS 变量覆盖写在 `:root` 块中
   - 暗色模式适配使用 `[data-theme='dark'] &` 嵌套选择器
   - 文章级样式限定在 `.single .content` 选择器内
   - 行内代码样式必须使用 `!important`
3. 使用 `AGENTS/templates/patch_format.md` 格式输出变更

**输出**：标准化补丁（patch_format.md 格式）

**判断标准**：

- 代码不包含对 `themes/FixIt/` 的任何修改
- 暗色模式适配完整
- 补丁格式符合模板要求

---

## Step 4：安全验证

**输入**：Step 3 输出的代码变更

**操作**：

1. 确认以下安全检查项：

| 检查项 | 要求 |
|--------|------|
| 是否误触 `themes/FixIt/` 源码 | 必须为否 |
| 亮色模式视觉效果 | 符合预期 |
| 暗色模式视觉效果 | 符合预期 |
| 文字与背景对比度 | ≥ 4.5:1（WCAG AA） |
| 数学公式渲染 | 正常 |
| 代码块语法高亮 | 正常 |
| 非目标页面未受影响 | 确认 |

2. 输出缓存清理与测试命令：
   ```bash
   rm -rf resources/_gen/ public/
   hugo server --disableFastRender --ignoreCache
   ```

**输出**：验证结果表（通过/未通过）

**判断标准**：所有检查项必须为"通过"，否则返回 Step 3 修正

---

## Step 5（强制）：更新日志

**触发时机**：Step 4 验证通过后

**操作**：

1. 按 `AGENTS/knowledge/dev_log.md` 第二部分定义的日志条目格式，输出一条日志
2. 日志必须包含：日期、事件简述、事件类型、触发原因、踩坑点、解决方案、对 Agent 的强制约束
3. 提示用户将日志条目追加到 `AGENTS/knowledge/dev_log.md`

**输出**：Markdown 格式的日志条目，示例如下：

```markdown
### [2026-04-20] 修复暗色模式行内代码对比度

- **事件类型**：样式修复
- **触发原因**：暗色模式下行内代码背景色与正文对比度不足
- **踩坑点**：行内代码样式被 Chroma 和主题多层覆盖，普通优先级无效
- **解决方案**：使用 `!important` 强制覆盖，暗色模式单独适配
- **对 Agent 的强制约束**：行内代码样式必须使用 `!important`，暗色模式必须使用 `[data-theme='dark'] &` 单独覆写
```

**判断标准**：日志条目格式完整，"对 Agent 的强制约束"字段必须包含可执行的规则
